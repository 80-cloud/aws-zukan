## 2. 収集の出典戦略（推測に頼らない）

### 出典の優先順位
1. **自分の一次体験**（開発記録）— 最優先。`realWorldNotes` に出典つきで。検証済みの事実。
2. **AWS 公式のサービス代表ページ**（概要・料金・クォータ・セキュリティ）— 安定した URL を `links` に。
3. **AWS Well-Architected Framework** — 評価8軸の判定根拠（→ 評価ルーブリック.md）。
4. **AWS 公式ドキュメント** — 機能・制約・上限の確認。

### 手順（三現主義）
- 題名・記憶で書かない。**公式ページ/ドキュメントを実際に読んでから**項目を埋める。
- 体験は `realWorldNotes{source}`（出典必須）、一般仕様は本文フィールド＋公式リンク。出典のない知識を体験として偽装しない。
- 料金は具体額を持たず、定性表現＋公式料金ページへ送客（金額は変わるため）。
- `updatedAt` / `verifiedAt` を記録。

### 「掲載可」の最小条件（1サービス）
固定スキーマの必須欄が埋まれば掲載可：`name / category / oneLiner / mainUseCases / notSuitableFor / links.overview / tier / updatedAt`。
`adoption` / `ops` / `costGotcha` / `realWorldNotes` は**分かる範囲で段階投入**。不明欄は**空のまま（捏造しない）**＝「未確認」を可視化する。

### バッチ運用
`zukan-data-ingest` スキルで N 件ずつ。1バッチ＝対象サービスを決め → 公式を読み → スキーマへ写経 → JSON 妥当性・表記一貫性を確認。

## 3. 「成立」の目安（達成状況）

- サービス：基盤・頻出は必須欄が全件埋まっている（当初目標 約42件を達成し、以降も継続拡充）。✅ 達成。
- 構成パターン：目標 8〜10件に対し **15件以上** を収録。✅ 達成。
- 各構成に標準推奨＋不適合（前提条件つき）＋評価8軸が揃う。✅ 達成。
- 受入条件（要件定義 A-1〜A-5）を満たす。

### 今後の任意拡充
- realWorldNotes（一次体験・出典必須）を、踏んだつまずきが出るたびに追記。
- verifiedAt から一定期間を過ぎた項目に「要確認」を出す鮮度管理。
- 個別項目化していない機能（Auto Scaling 等）の追加。
