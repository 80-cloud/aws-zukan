# aws-zukan 技術スタック

**バージョン:** 0.1
**作成日:** 2026-06-26

最初の版（Phase 1）はフロントエンド先行・ローカル完結で作り、データの読み込みを差し替え可能な層に隔離する。サーバ側（Phase 2）は Java 25 を中心とした構成を計画として定める。

---

## 1. Phase 1（最初の版・現行）

| 区分 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | データの形を型で固定し、項目の取り違え・欠落を型で防ぐ |
| UI | React + Vite | 高速な開発サーバ・既存アプリと同じ操作感を踏襲 |
| スタイル | Tailwind CSS | 図鑑の一覧・比較表を素早く組む |
| ルーティング | React Router | 一覧／詳細／比較の画面遷移 |
| 状態管理 | React Context ＋ Hooks | 閲覧専用で軽量。大型の状態ライブラリは持ち込まない |
| データ源 | JSON（`src/data/`） | サービス台帳・共通ルール・構成パターンを同梱データで持つ |
| データ読み込み | `src/api/` で隔離 | 将来サーバAPIへ無改修で差し替えるための境界 |
| ローカル保存 | localStorage | お気に入り・既読などの閲覧状態のみ |
| 検索 | クライアント側インデックス | 件数増に備え軽量な全文インデックス（例：MiniSearch）を検討 |
| テスト | Vitest ＋ Testing Library | ロジック・コンポーネントの単体／結合 |
| 静的検査 | ESLint ＋ Prettier ＋ TS strict | 早く軽く問題を落とす |

**ローカルポート:** Vite `5176`（他アプリの 5173 / 5175 と分離して並列起動可能にする）。

---

## 2. Phase 2（サーバ側・計画）

データを共有・更新・大規模検索したくなった段階で、`src/api/` の差し替え先として下記を立てる。

| 区分 | 採用 | 理由 |
|---|---|---|
| 言語 | **Java 25** | 長期サポート版。下の §3 のとおり図鑑のデータ・検索と相性が良い |
| フレームワーク | Spring Boot 3.5.x | Web／データアクセス／将来の認証まで一貫 |
| ビルド | Gradle 9.x | Java 25 ツールチェーンに対応 |
| データアクセス | Spring Data JPA | リポジトリ層を薄く保つ |
| DB | PostgreSQL 16（Docker） | 関係データ＋全文検索を1つで賄える |
| マイグレーション | Flyway | スキーマ変更を追跡可能・実行順保証 |
| 全文検索 | PostgreSQL `pg_trgm` / GIN 索引 | 数百サービスの横断検索を後方一致まで含めて最適化 |
| API | REST `/api/v1/` | バージョンを切って後方互換を保つ |

**接続の切り替え方:** フロントの `src/api/` は最初 JSON ＋ localStorage を返す実装。Phase 2 で同じインターフェースのまま REST 呼び出しへ差し替える（画面側は無改修）。

## 3. なぜ Java 25 と相性が良いか

図鑑は「**項目が決まった大量データ**」と「**読み取り中心の検索**」が中心であり、Java 25 の特徴がそのまま噛み合う。

- **レコード（record）**：サービスや構成パターンは項目が固定。レコードで不変なデータ運搬オブジェクトを素直に表現でき、テンプレート設計（決まった項目を埋める）とそのまま対応する。
- **シールドな型（sealed interface）**：評価の観点やカテゴリのような「取りうる種類が限られる」概念を型で閉じて、抜け漏れをコンパイル時に検出できる。
- **仮想スレッド**：読み取りリクエストが多い図鑑APIで、少ない資源で多数の同時アクセスをさばける。
- **パターンマッチ**：構成パターンの分岐表示・整形を簡潔に書ける。
- **PostgreSQL ＋ 全文検索 ＋ Flyway**：数百件規模の検索とスキーマ進化に耐える、実績のある組み合わせ。
- **Spring Boot 3.5.x / Gradle 9.x**：いずれも Java 25 に対応し、Web・データ・将来の認証まで一式そろう。

---

## 4. インフラ

- **Phase 1**：ローカル完結（外部サービスなし）。公開やサーバ構築は持たない。
- **Phase 2 以降**：まずローカルの Docker でサーバ＋DB を動かす。公開先（クラウド等）は、その時点で必要性・費用・運用負荷を見て**改めて選ぶ**（既定で特定クラウドにはしない）。

---

## 5. 現時点で持ち込まないもの

| 項目 | 理由 |
|---|---|
| 大型の状態管理ライブラリ | 閲覧専用には過剰 |
| バックエンド・DB（Phase 1） | 読み取り中心の同梱データで足りる |
| 認証基盤 | 書き込み・共有が必要になってから |
| 料金の自動取得 | 金額は変わりやすく、おおまかな表現＋公式誘導で足りる |
