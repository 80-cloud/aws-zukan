## 0. 品質の方針

このアプリで守る品質の下限と、特に力を入れる点をはじめに決めておく。

### 品質の下限（全体で満たす基準）

安定性・セキュリティ・保守性・性能/UX のいずれの観点でも一定の基準を満たすことを前提に設計する。どれか一つでも基準を下回らないように作る。

### 特に重視する観点：保守性・拡張性

本アプリの目玉は「**要件に対する構成の良し悪しをまとめた設計判断集**」と、「**30件から300件規模まで破綻なく増やせるデータ構造**」である。そのため **保守性・拡張性** を特に重視して設計する。

具体的には、新しいサービスや構成を**追加するだけで**一覧・検索・比較に反映され、表示側のコードを書き換えずに増やせること。データの読み込みは差し替え可能な層に隔離し、はじめは JSON とブラウザ内保存、将来はバックエンドへ無理なく移せる構造にする。

### 守る前提（重視する観点のために他を犠牲にしない）

保守性に力を入れる一方で、次は基準以下に落とさない：
- **性能・UX**：300件規模でも検索・絞り込み・比較が即時に返る。
- **セキュリティ**：入力項目を決まった形に固定し（自由記述に頼らない）、本文を描画する際の安全処理を行う。

## 1. プロジェクト概要

### 1-1. 目的

AWS は数百のサービスがあり、「どれが何をするか」「似たサービスの違い」「どう組むのが妥当か」を横断的に把握しづらい。本アプリは次を引けるようにする。

- 個々のサービスを「部品表」として調べる（サービス図鑑）
- ある要件に対する**標準推奨構成・不適合になりやすい構成**を「設計判断集」として調べる（構成パターン図鑑）

### 1-2. 対象ユーザー

AWS を学ぶ人。設計判断の素地づくりに使う。

### 1-3. スコープ

最初の版は **閲覧専用・ローカル完結**。基盤として使われる主要サービス30〜50件を厚く載せ、構成パターンを5〜10件用意する。残りのサービスは後から段階的に増やす。

### 1-5. 差別化ポイント

必要のない仕組みを持ち込まず構成をシンプルに保つ方針で、公式ドキュメントとの違いを挙げる。

| 項目 | 公式ドキュメント | 本アプリ |
|---|---|---|
| 主眼 | 1サービスの網羅的な仕様 | 横断比較＋構成単位の設計判断 |
| 料金 | 正確だが複雑・常に変動 | おおまかな表現（無料枠の有無／課金の軸／相対感）＋公式の料金ページへ誘導 |
| 良し悪し | 断定しない | 「標準推奨／不適合になりやすい」と前提条件つきで示す |
| 設計の確認 | なし | 要件から「確認すべき論点」を返す（将来） |

---

## 2. 前提条件と制約

- 最初の版は閲覧専用。ログイン・投稿・編集・ファイルアップロード・外部通信を持たない。
- 内容は同梱した JSON データを元にする。お気に入りや既読などの閲覧状態だけブラウザ内に保存する。
- 料金は具体的な金額を持たず、おおまかな表現と公式の料金ページへの誘導にとどめる（金額は変わりやすいため）。
- 各項目は決まったテンプレートに沿って埋める。自由記述に頼らず、内容のばらつきと誤りを抑える。

## 3. 機能要件（Phase別スコープ）

### Phase 1（最初の版）

| ID | 機能 | 優先度 | 説明 |
|---|---|---|---|
| F-SVC-01 | サービス図鑑 一覧 | MUST | カテゴリ分類・検索・絞り込み。主要30〜50件。 |
| F-SVC-02 | サービス詳細 | MUST | テンプレート項目（一言／使う場面／向かない場面／関連／代替／導入の難易度／公式リンク／更新日 など）を表示。 |
| F-PAT-01 | 構成パターン図鑑 一覧 | MUST | 「何を実現したいか」から推奨構成を探す。5〜10件。 |
| F-PAT-02 | 構成パターン詳細 | MUST | 標準推奨構成・不適合になりやすい構成・評価の観点・必須になりやすい統制・任意要素・代替案。 |
| F-CMP-01 | 比較ビュー | MUST | 同じ目的に対する複数構成を評価の観点ごとに並べて比較。 |
| F-DATA-01 | データ駆動 | MUST | サービス／共通ルール／構成パターンを JSON から読み込む。読み込み層は差し替え可能に分離。 |
| F-FAV-01 | 閲覧状態の保存 | SHOULD | お気に入り・既読をブラウザ内に保存。 |

## 4. 非機能要件（品質の具体化）

### 4-1. 保守性・拡張性（特に重視）

- 表示・データ読み込み・状態管理・型定義を分ける。
- データ読み込みを差し替え可能な層（`src/api/`）に隔離し、JSON／ブラウザ内保存 → 将来のバックエンドへ無理なく移せるようにする。
- TypeScript でデータの形を型で定義し、整合性を型で守る。
- サービスや構成パターンの**追加点を3か所**（サービスの形・構成パターンの形・共通ルールの参照）に明確化し、追加が表示側の改修なしで反映されることを確認する。
- IAM・ログ・暗号化・ネットワーク・バックアップ・タグ・障害対応などの**共通ルールは1か所にまとめ**、各サービスには固有の違いだけ書く（重複を作らない）。

### 4-2. 性能・UX

- 件数が増えても全件を一度に描画しない（ページングや仮想化）。
- 検索は小規模なら単純一致、件数が増えたらブラウザ内の索引化を検討する。
- アクセシビリティに配慮する（ラベル・代替テキスト・キーボード操作・色だけに頼らない表現）。
- 比較は評価の観点を記号や3段階で持ち、表としてすぐ描けるようにする。

### 4-3. 保守性（実装ルール）

- すべての変更は Issue・ブランチ・PR を通す。
- 例外処理は握り潰さず一元的に扱う。
- 画面を伴う変更は実ブラウザで確認する。

### 4-4. セキュリティ

- 本文を Markdown などで描画する場合は、変換後に安全でない要素を除去し、安全が確認できない直接埋め込みは行わない。
- 入力項目を決まった形に固定し、内容起因の誤りや不正な入力の余地を減らす。
- 将来バックエンドやホスティングを持つ際は、通信元の制限やセキュリティヘッダを付与する。

## 5. 対象外（スコープ外）

- ログイン・アカウント・権限管理（最初の版では持たない）。
- 投稿・編集・ファイルアップロード。
- バックエンド・データベース・本番公開。
- 料金の具体的な金額や自動取得。
- 構成の変更履歴・テンプレートの複製編集・構成へのレビューコメント・サービス採用履歴（利用者が書き込んで記録する機能）。本アプリは調べるための図鑑に絞り、設計・レビューを管理するツールには広げない。

## 6. 受入条件

- **A-1**: サービス図鑑で主要サービスの全件にカテゴリ／検索／絞り込みで到達でき、詳細のテンプレート項目が表示される。
- **A-2**: 構成パターン詳細で「標準推奨構成」「不適合になりやすい構成」「評価の観点」が前提条件つきで表示される（良し悪しを断定する表現がない）。
- **A-3**: 比較ビューで同じ目的の2構成以上を評価の観点ごとに並べられる。
- **A-4**: 新しいサービスを1件、データに追加するだけで（表示側の改修なしで）一覧・詳細・検索に反映される。
- **A-5**: 300件相当のダミーデータでも一覧・検索が体感で即時に返る。

## 7. 用語集（本アプリ内）

- **サービス図鑑**：個々のサービスを調べる「部品表」。
- **構成パターン図鑑**：要件に対する推奨/不適合構成と評価をまとめた「設計判断集」。
- **共通ルール**：IAM・ログ・暗号化などの横断ルール。各サービスから参照し、重複させない。
- **標準推奨構成 / 不適合になりやすい構成**：良し悪しを断定せず、前提条件つきで示す表現。

## 8. データモデル設計方針

3つの層で持つ。

| 層 | 主語 | 役割 |
|---|---|---|
| サービス層 | EC2・S3・RDS など | 個々の特徴・制約・運用の前提 |
| 構成パターン層 | 静的サイト公開・社内Web・バッチ処理 など | 要件に対する推奨/不適合構成と評価 |
| 共通ルール層 | IAM・ログ・暗号化 など | 横断ルール（各サービスから参照） |

- サービス層・構成パターン層は決まったテンプレート（項目セット）で持ち、追加を容易にする。
- 構成パターンの評価は複数の観点（セキュリティ・可用性・運用負荷・コスト・拡張性・統制への適合・移行のしやすさ・特定サービスへの依存度）を3段階などで持ち、比較表としてすぐ描けるようにする。
- 画面の多くは同じデータの見せ方違い（一覧／目的引き／比較／絞り込み）であり、データの形を先に固める。
- サービス・構成パターンは「実際に踏んだつまずき」を出典リンクつきで持てる。推測でなく検証済みの事実だけを載せ、内容の信頼性を保つ。

## 10. リスク・前提（R-* 形式）

| ID | リスク | 対策 |
|---|---|---|
| R-01 | 数百件を埋めきれず未完成になる | まず主要30〜50件で成立させ、残りは段階的に増やす。 |
| R-02 | 料金情報が古くなる | 具体的な金額を持たず、おおまかな表現と公式ページへの誘導にする。 |
| R-03 | 設計の確認が誤った内容を返す | 用意した構成パターンを引く形に限定し、その場で文章を生成しない。 |
| R-04 | 内容の事実誤り | 実務寄りの記述は一般的な範囲にとどめ、組織ごとに変わる情報は別の層に分ける。つまずきは推測でなく実際に踏んだ事実を出典つきで載せる。 |

| ID | 内容 | 状態 | 将来 |
