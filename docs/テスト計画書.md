# aws-zukan テスト計画書

**バージョン:** 0.1
**作成日:** 2026-06-26

> 関連：[要件定義書](./要件定義書.md) ／ [機能一覧](./機能一覧.md) ／ [ER図](./ER図.md) ／ [派生ビュー規則](./派生ビュー規則.md) ／ [コンテンツ計画](./コンテンツ計画.md)

このアプリは「**データ（図鑑の中身）が主役**」で、特に重視する観点は保守性・拡張性。よってテストの中心は **データ整合性**と、**サービスを足しても表示・検索が壊れないこと**に置く。

---

## 1. 目的とスコープ

### 目的
図鑑の品質を測定可能なテストで担保する。中心は「データが正しく・参照が壊れず・追加で壊れない」こと。

### スコープ（Phase 1）
閲覧専用フロント：サービス図鑑（一覧/詳細/検索）・構成パターン図鑑・比較・派生ビュー（設計レビュー観点チェック／セキュリティ注意カタログ）・データ読み込み。認証・書き込み・バックエンドは持たないため対象外（Phase 2 に予約）。

---

## 2. テストレベル

| レベル | 対象 | 手段 |
|---|---|---|
| データ検証 | seed JSON（services/patterns/common-rules）のスキーマ準拠・参照整合・出典 | Vitest（データ駆動）／スクリプト |
| フロント単体 | コンポーネント・検索/フィルタ・Markdown 描画のサニタイズ | Vitest + Testing Library |
| 派生ビュー | F-CHK-01／F-SEC-01 の生成規則どおりに組み立つか | Vitest |
| アクセシビリティ | ラベル・代替テキスト・キーボード操作・色依存回避 | jest-axe ＋ 手動 |
| E2E / 疎通 | 一覧 → 詳細 → 比較 の主要導線 | Playwright（または手動疎通） |
| （Phase 2）バックエンド | Controller→Service→DB・API | JUnit 5 ＋ Testcontainers(PostgreSQL) |

---

## 3. テスト技法

- **データ駆動**：全サービス・全構成パターンをループして同じ検証をかける（1件の見逃しも残さない）。
- **境界値**：検索語 0/1/長文、タグ 0件/多数、比較対象 1/2/多数、評価記号の範囲外。
- **同値分割**：tier 1/2/3、cost.relative 低/中/高、評価 ◎○△✕。
- データ整合性は「正常系より**壊れているケース**を厚く」書く（重視する観点の本質は「追加・変更で壊れない保証」）。

## 6. ★ データ整合性マトリクス（中核）

seed データに対し、以下を**全件**検証する。1つでも失敗したら「掲載不可」。

| ケース | 検証内容 | 期待 |
|---|---|---|
| スキーマ準拠 | 全 service/pattern が必須欄（name/category/oneLiner/links.overview/tier 等）を持つ | pass |
| 参照解決 | `pattern.recommendedStack` / `antiPatterns[].stack` / `stackRoles[].serviceId` / `companions[].serviceId` / `alternatives` / `related` が**実在の service.id** を指す | 全解決（未解決0） |
| 共通ルール参照 | `commonRuleRefs` が実在の common-rule key を指す | 全解決 |
| 評価値の範囲 | `evaluation` の8軸が ◎/○/△/✕ のいずれか | pass |
| 出典の必須 | `realWorldNotes[].source` / `antiPatterns[].source`(非null時) が `http` で始まる | pass |
| ID 一意 | service.id / pattern.id に重複がない | pass |
| 出典の不足検出 | `realWorldNotes` に source の無い項目がない（体験は必ず出典つき） | pass |
| 鮮度の区別 | `verifiedAt` が一定期間より古い項目を「要確認」として区別できる | pass |
| **拡張で壊れない** | サービス/構成を1件追加するだけで、一覧・検索・詳細・比較が表示側無改修で反映される | pass |

> 「拡張で壊れない」は、このアプリで特に重視する保守性・拡張性を自動で守る要。CI に組み込む。

## 7. ★ 推奨品質・原則適合マトリクス（中核その2）

> 表示崩れより危険なのは「推奨構成の誤判定」。図鑑が出す推奨・注意・表現が設計の原則に沿うかを、全構成パターンに対して検証する。

| 観点 | 検証内容 | 期待 |
|---|---|---|
| 過剰構成を推奨しない | 目的に対し `recommendedStack` が過剰でない（例：静的サイトの第一候補に理由なく EC2/RDS/ALB を入れない） | pass |
| 不足構成を推奨しない | 外部公開・動的処理の構成で、認証/ログ/監視などの必須統制が `requiredGovernance` から欠けていない | pass |
| 条件で確認が増える | 個人情報・外部公開などの前提が付く構成は、確認項目（`requiredGovernance`／レビュー観点）が増える | pass |
| 例外を残す | あるサービスが不適合寄りでも、既存資産・特殊ミドル等の例外が `suitableConditions`／`notes` に示される（一律不適合にしない） | pass |
| 断定しすぎない | 文言に「正解」「不正解」「一択」などの断定語が無く、「この前提では〜」の条件つき表現になっている | 断定語 0件 |

> 「断定しすぎない」は断定語の自動検査で守れる（このアプリの「良し悪しを断定しない」方針の自動担保）。残りは内容レビュー＋一部データアサート（例：静的サイトの `recommendedStack` に ec2/rds が含まれない）で確認する。

## 9. アクセシビリティ・性能・堅牢性

- **アクセシビリティ**：ラベル・代替テキスト・キーボード操作を満たす。**危険度（◎○△✕・警告）は色だけに頼らず、アイコン・文章でも判別できる**ようにする（jest-axe＋手動）。
- **堅牢性（壊れ方の設計）**：localStorage や JSON の破損・読み込み失敗でも、画面全体がエラーにならずフォールバック表示する（要件 §1-3）。
- **性能（ローカルバジェット・正直な現状認識）**：

| 操作 | 目標（P95・ローカル） |
|---|---|
| 初回表示 | ≤ 1.5s |
| 検索・絞り込み応答 | ≤ 100ms（300件相当のダミーで） |
| 詳細・比較表の描画 | ≤ 100ms |

> Phase 2 でサーバ／DB が入ると条件が変わるため、その時点で実計測に基づき再定義する。
