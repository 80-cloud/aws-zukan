# aws-zukan — AWS 設計判断の図鑑

[![Data Check](https://github.com/80-cloud/aws-zukan/actions/workflows/data-check.yml/badge.svg)](https://github.com/80-cloud/aws-zukan/actions/workflows/data-check.yml)

[![Deploy to Pages](https://github.com/80-cloud/aws-zukan/actions/workflows/deploy.yml/badge.svg)](https://github.com/80-cloud/aws-zukan/actions/workflows/deploy.yml)

AWS のサービスを「部品表」として引くだけでなく、「どう組み合わせるか」「どんな構成が向く／向かないか」までを前提条件つきで引ける図鑑アプリです。

🔗 **ライブデモ: https://80-cloud.github.io/aws-zukan/**

100 を超えるサービスと 20 以上の構成パターン、そして横断ルールを収録しています（正確な件数はアプリ内に常に最新が表示されます）。

## 解きたい課題

AWS は数百のサービスがあり、公式ドキュメントは「各サービスが何をするか」は詳しい一方、「この要件にはどの構成が妥当か」「何を見落とすと事故るか」は横断的に引きにくい。学習者や設計に不慣れな人が「動くけれど本番に足りない構成」を作ってしまいがちです。

そこで、サービス単体ではなく構成（設計判断）と横断ルールまでを一つの図鑑にまとめ、検索・比較・レビュー観点まで引けるようにしました。

## 主要機能

- **サービス図鑑**：100 を超える AWS サービスを、用途・注意点・出典つきで一覧・比較できる。
- **構成パターン図鑑**：20 以上の構成を「どんな要件に向く／向かない」まで前提つきで収録。
- **共通ルール**：ネットワーク・IAM・暗号化などの横断ルールを正規化し、重複なく参照。
- **8 軸評価**：Well-Architected の 6 本柱＋独自 3 軸で、各構成を ◎○△ で表示。
- **派生ビュー**：設計レビュー観点・セキュリティ注意・隠れコスト・事例検索・不適合構成を、同じデータから自動で組み立て。
- **鮮度管理と検索**：確認日が古い項目に「要確認」を付け、タグや課題から逆引きできる。

## アプローチと差別化

| 差別化 | 中身 |
|---|---|
| 2 層 ＋ 横断ルールのデータモデル | サービス図鑑（部品表）／構成パターン図鑑（設計判断集）／共通ルール（ネットワーク・IAM・暗号化等を正規化し重複記述しない） |
| 断定しない | 「正解／不正解」ではなく「標準推奨構成／不適合になりやすい構成」を前提条件つきで示す |
| 8 軸で評価 | Well-Architected の 6 本柱＋独自 3 軸（統制適合・移行容易・ベンダー依存）を ◎○△ で表示 |
| 創作しない | 本文・公式を読んでから書き、体験ベースの記述は出典必須。確認できない欄は空のままにして未確認を可視化 |
| 派生ビューは文章生成に頼らない | 設計レビュー観点・セキュリティ注意・隠れコスト・事例検索・不適合構成は、既存データからルールベースで機械的に組み立て |

## 3 つの引き方

| 引き方 | 主な画面 | 使う場面 |
|---|---|---|
| 部品から引く | サービス一覧 / 比較 | 「このサービスは何？」「どちらを選ぶ？」 |
| 構成から引く | 構成パターン | 「この要件、どう組む？」 |
| 課題から引く | 事例 / 不適合になりやすい構成 / 設計レビュー観点 | 「自分は何を見落としている？」 |

## 派生ビューのしくみ（このアプリの中心）

「設計レビュー観点」「セキュリティ注意」「隠れコスト」「事例検索」「不適合構成」は、**追加で書いたデータではありません。** 同じ元データから、別の切り口を毎回その場で組み立てています。文章の自動生成には頼っていません。

| ビュー | 何を組み立てるか | 実装 |
|---|---|---|
| 設計レビュー観点 | 必要な統制＋共通ルール＋評価の弱い軸を束ねてチェックリスト化 | [`reviewChecklist.ts`](frontend/src/lib/reviewChecklist.ts) |
| セキュリティ注意カタログ | 全構成のセキュリティ系の注意点を横断集約 | [`securityCatalog.ts`](frontend/src/lib/securityCatalog.ts) |
| 隠れコスト辞典 | 想定外の課金軸（転送量・NAT・ログ・残存課金…）を横断抽出 | [`costDictionary.ts`](frontend/src/lib/costDictionary.ts) |
| 事例（課題）検索 | 業務課題のタグから、該当する構成を逆引き | [`scenarioIndex.ts`](frontend/src/lib/scenarioIndex.ts) |
| 不適合になりやすい構成 | 各構成の「この前提では不適合」をサービス単位で逆引き | [`antiPatternCatalog.ts`](frontend/src/lib/antiPatternCatalog.ts) |
| 情報の鮮度管理 | 確認日が古い項目に「要確認」を付け、経年劣化を可視化 | [`freshness.ts`](frontend/src/lib/freshness.ts) |

同じ元データから導くので、**画面ごとに情報がずれません。** データを 1 か所直せば、すべてのビューに反映されます。

## 内容の正しさをどう担保しているか

図鑑である以上、書いてあることが間違っていたら価値がありません。次の 4 つを守っています。

1. **公式ドキュメントの本文を読んでから書く**（題名や記憶だけで書かない）
2. **体験にもとづく記述には出典 URL を必ず付ける**
3. **確認できなかった項目は、埋めずに空欄のままにする**（分からないことが分かるように出す）
4. **CI で機械的に検査する**

CI は 3 本あります。

| ワークフロー | 検査内容 |
|---|---|
| [Data Check](.github/workflows/data-check.yml) | 参照切れ（存在しないサービス id）／必須項目の欠落／ID 重複／評価値が定義外／出典 URL の形式／断定的な言い回しの検出 |
| [Docs Lint](.github/workflows/docs-lint.yml) | 用語・命名の統一 |
| [Deploy to Pages](.github/workflows/deploy.yml) | ビルドと公開 |

実際に公式を読み直したことで、**すでに新規受付を終了していたサービスを掲載前に除外**できました。記憶や古い前提のまま書いていたら、そのまま誤りとして残っていた箇所です。

## 設計判断の記録

なぜその作りにしたのかを、あとから追えるように残しています。

- [ADR 一覧](docs/ADR/) — 2 層データモデル / 8 軸評価 / 派生ビューのルールベース化 / 断定しない表現

## 拡張に強い構造

- **データを足すだけで増える** — サービス／構成を JSON に追加するだけで一覧・検索・比較に反映され、表示側のコードは書き換え不要。
- **読み込みを 1 か所に隔離** — データアクセスは [`src/api/zukanRepository.ts`](frontend/src/api/zukanRepository.ts) だけを通します。将来 JSON からバックエンドへ載せ替えても、画面は無改修で済む構造です。
- 数十件から数百件の規模まで破綻しない構造を狙っています。

## 作るうえで大事にしたこと

- **すぐ触れること** — URL を開けば動きます。main への反映で自動デプロイされます。
- **説明が古くならないこと** — 収録件数は文章に書き込まず、データから数えて表示しています。中身が増えても説明が陳腐化しません。
- **分からないことを埋めないこと** — 空欄のまま出します。埋めるために作らないことを優先しました。
- **判断の理由を残すこと** — なぜそう作ったかを記録に残し、あとから検証できるようにしました。

## 現時点で対象にしていないこと

- ユニットテスト・E2E テストは現時点では対象にしていません。データの整合性は上記の Data Check で検査しています。
- 書き込み・ログイン・複数人での利用は行いません。閲覧専用でブラウザ内に完結します。

## AI の活用方針

設計・実装・レビュー・ドキュメント作成の各工程で、AI コーディングツールを活用しています。使い方の方針を明確にしておきます。

- **設計判断と最終責任は自分が持つ**：AI の提案はそのまま採用せず、意図と根拠を理解したうえでレビューして取り込んでいます。
- **動作は必ず自分で検証する**：ビルド・型チェック・データ整合性チェック（CI）のグリーンを確認してから反映しています。
- **道具として使いこなす**：AI を開発を速める道具と位置づけ、品質と成果物の責任は自分にあります。

## 技術スタック

- フロントエンド: React 19 / Vite 6 / TypeScript / Tailwind CSS 4 / React Router
- データ: JSON（`data/`）を `src/api/` のリポジトリ層だけから読む隔離設計
- CI/CD: GitHub Actions（データ整合性チェック・用語チェック・GitHub Pages 自動デプロイ）

## ローカル開発

- 依存導入: `npm --prefix frontend install`
- 開発サーバー: `npm --prefix frontend run dev`（http://localhost:5176）
- ビルド: `npm --prefix frontend run build`（型チェック + 本番ビルド）

コミット前に用語・命名チェックが自動で走ります（初回のみ `bash scripts/install-hooks.sh`）。

## ロードマップ

- **Phase 1（現在）**: 読み取り図鑑 — サービス／構成パターン／共通ルールと、ルールベースの派生ビュー（設計レビュー観点・セキュリティ注意・隠れコスト・事例・不適合構成・鮮度管理）。
- **Phase 2（構想）**: 組織統制層 — 承認の要否・標準構成・社内標準との差分・監査証跡・アカウント配置・責任分界など、企業／グループ利用向けの統制機能。文章生成に頼らずルールベースで組み立てる方針は維持し、データ読み込みを `src/api/` に隔離した現構造の上にバックエンド（Java / Spring Boot）と認可を載せます。
